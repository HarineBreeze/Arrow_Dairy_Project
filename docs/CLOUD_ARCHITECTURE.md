> 状态：**设计稿 / 施工图**，尚未实施。

> 基线：截至 v4.9.48，项目仍是 100% 本地单机、无任何网络依赖。文中所有现况描述均以源码为准并标注文件/符号。

## 0. 一句话结论

**内容不上云守的是隐私与数据主权，权益上云换的是管理权——两者不矛盾，正好构成战略的两条腿。**

要"远程给某个 ID 加 VIP / 开关功能"，本质要求是服务端能单方面改变用户状态并让它生效。因此身份与权益必须由服务端权威；日记等用户内容仍留在本地。本文剩下的部分就是把这句话拆成字段、表结构、同步规则和施工步骤。

## 2. 核心原则：权威上云，不是数据上云

本地可以保存和云端一模一样的副本，但**最终以谁为准**决定了谁能管理谁。

- 若 VIP / 灵感只存在本机：服务端无处可写；就算改了本地文件，下次同步本地旧值会反向覆盖云端——**管理权为零**。
- 因此：想保留"远程给谁加 VIP、封谁、开哪个功能"的能力，这些状态就**必须有且只有服务端说了算**。这是定义，不是选择题。

---

## 3. 数据分层：三类数据的权威划分（写死，不许临时改）

| 类别 | 字段 / 内容 | 权威方 | 是否上云 | 理由 |
|---|---|---|---|---|
| **A. 用户内容** | 日记、物品、资产、倒计时、回收站 | 本地设备 | 否（或仅加密镜像，用户主动开启） | 隐私敏感，是"数据主权"卖点的核心 |
| **B. 契约账本** | `userId`、`points`、`badge`、`ownedBadges`、`redeemedCodes`、`vipCardCount`、`vipWeekCardCount`、`vipCardExpireAt`、`banned`（新增） | **服务端** | **是（必须）** | 这是"你和用户的关系记录"，不是用户隐私；不上云则无法管理 |
| **C. 运营控制** | `featureFlags`（新增）、公告、商品上下架 | **服务端** | **是（必须）** | 灰度、授权、远程开关功能、出问题不用发版 |

补充说明：

- B 类不是"用户的数据"而是"你们之间契约的记录"。云端存"账号 VIP 到 2026-12-01"隐私顾虑极低，合规压力小；这与"不碰用户内容"的承诺不冲突。
- `lastWriteReward`（每日首发奖励日期）虽然记在本地，但因为灵感（`points`）已服务端权威，它最终也要以云端为准，否则用户改本地日期可无限刷分。
- `nickname` / `gender` / `avatarPath` / `registeredAt` 归 A 类（本地权威），但云端可留只读副本用于展示。

## 4. 云端权益表结构（最小可行）

一张表即可，**日记内容一行都不上云**。以 `userId` 为唯一索引。

| 字段 | 类型 | 说明 |
|---|---|---|
| `userId` | string (PK) | 本地生成的顺序 ID，云端认它为主键 |
| `vipExpireAt` | string (ISO8601) | VIP 到期时间；空 = 无生效中限时权益。对应本地 `vipCardExpireAt` |
| `points` | int | 剩余灵感 |
| `ownedBadges` | json array | 已拥有身份，`normal` 恒在首位 |
| `badge` | string | 当前佩戴身份 |
| `redeemedCodes` | json array | 已用兑换码（无限次码不入列） |
| `vipCardCount` / `vipWeekCardCount` | int | 限次卡已兑次数，与本地规则一致（30 / 6 上限） |
| `banned` | bool | 封禁标记（新增，本地目前无） |
| `featureFlags` | json object | 功能开关（新增，如 `{"cloudSync": true}`） |
| `updatedAt` | string (ISO8601) | 服务端最后修改时间，用于同步比对 |

**运营动作示例**：给 `userId=10001` 加 7 天 VIP = 改该行 `vipExpireAt`（未过期则在原值上 +7 天，已过期则从当前时间起算）+ 把 `badge` 标为 VIP。用户下次同步自动生效。

## 5. userId 约定（身份锚点，不许乱改）

1. **生成**：本地首次启动自增分配（`10001` 起），固化进 `user_profile.json`；已分配最大序号单独存 `user_id_seq.json`，保证删档不回退、跨重启不重复发号。
2. **云端认它为主键**：换机导入必须把 userId 带过去，否则云端认成新用户，权益全丢。
3. **不要改小**：手动改 userId 为已存在号会与云端主键冲突；如需重置，走专门流程（同时重置 seq 文件）。
4. **身份绑定（两阶段演进）**：
   - 阶段 2（起步）：匿名登录 + 本地 userId 绑定，用户无感。
   - 后期：账号密码登录，**账号作为访问该 userId 的凭证，不新建云端 uid**（详见第 12 节）。用于跨设备、权益找回、云同步；uid 归属不变，仍以本地生成值为准。

## 6. 同步与合并规则（按字段粒度，不整包覆盖）

**铁律：禁止用整份 profile 互相覆盖。** 否则会出现"加了 VIP 结果昵称被回滚"。

| 字段类别 | 同步方向 | 冲突处理 |
|---|---|---|
| A 类（内容/昵称/头像） | 本地 → 云（若开启同步） | 本地优先；按 `updatedAt` 较新者胜 |
| B 类（权益） | 云 → 本地（单向） | **云端绝对优先**，本地值永不回写覆盖 |
| C 类（功能开关） | 云 → 本地（单向） | 云端绝对优先 |

流程：

1. APP 启动 / 重新联网 → 用 userId 拉取 B/C 类权威状态。
2. 与本地快照比对 → 覆盖本地 B/C 字段，触发 UI 刷新（`UserStorage.revision` 现有机制可复用）。
3. 用户内容按 A 类规则（如开启云同步）单独处理，与权益解耦。

---

## 7. 离线策略（兑现"不锁数据"承诺）

- 本地始终保留最近一次同步下来的**权益快照**。
- 断网、欠费、云端不可达时：APP 用本地快照继续正常运行，**数据和功能都不被云端绑架**。
- 重新联网后再对齐权威状态（可能降级，如运营撤回体验权益——但用户数据绝不受影响）。
- 这是"欠费不锁数据"的技术保障：云是增值层，不是开关。

---

## 8. 安全边界

- **写权限只在服务端/管理端**。客户端绝不能写 B/C 类字段，否则用户改一下本地 JSON 就能给自己发 VIP。
- 云端权益接口必须鉴权（匿名 token 只读自己的；管理端写操作单独鉴权）。
- 内容若上云，走用户主动开启 + 端到端或传输加密；默认不上传。
- 兑换码规则（一码一次、大小写不敏感、无限次码例外）在服务端复刻，本地现有实现作为离线兜底，联网后以服务端裁决为准。

## 12. 账号密码身份体系（后期，对应 uid）

> 决策方向：后期引入账号密码，账号对应本地已有的 userId。

### 12.1 核心定义

- **账号是"钥匙"，不是"新身份"**：账号密码只是访问某个 uid 的凭证，**不新建云端 uid**。
- **绑定而非注册新号**：用户在本机已有 uid（本地生成，`10001` 起），注册时把这个 uid 绑到账号上，历史数据 / 灵感 / VIP 原地保留。
- **换设备 = 凭账号找回同一个 uid**，权益跟着 uid 走，不跟设备走。

### 12.2 三条不可违背的约束

1. **uid 归属不变**：仍以本地生成值为准（第 5 节）。账号表用 `userId` 作为关联键，一对一绑定。
2. **登录可选、绝不设登录墙**：首次安装仍可完全离线使用（本地自动发号、功能不受限）。登录只为跨设备 / 云同步 / 权益找回三个增值目的。若做成"不登录不能用"，直接违背"本地为根"战略。
3. **存量迁移走"绑定现有数据"**：当前本机 uid=10001 已有档案，必须走绑定流程；**禁止**走"注册新号生成新 uid"，否则权益和内容对不上。

### 12.3 数据结构（账号表，与权益表分离）

| 字段 | 类型 | 说明 |
|---|---|---|
| `accountId` | string (PK) | 账号标识（手机号 / 邮箱 / 用户名，待定） |
| `userId` | string (UNIQUE) | 绑定的 uid，一对一，指向第 4 节权益表 |
| `passwordHash` | string | bcrypt / argon2 **加盐哈希**，绝不存明文 |
| `createdAt` / `lastLoginAt` | string (ISO8601) | 审计 |

账号表与权益表分离：改密码不影响权益，封禁/权益展示也不用碰账号字段。

### 12.4 安全要求（硬性）

| 项 | 要求 |
|---|---|
| 密码存储 | 服务端 bcrypt / argon2 加盐哈希，绝不明文、绝不可逆 |
| 本地存储 | **只存 token，不存密码**；token 用 `flutter_secure_storage` 落 Android Keystore / iOS Keychain |
| 传输 | 全程 TLS |
| token 生命周期 | 登录发 access + refresh token，过期刷新，登出即清除 |
| 找回 | 手机号 / 邮箱验证找回，不提供"安全问题"这类弱验证 |

### 12.5 引入时机

放在阶段 2 之后：先用匿名绑定跑通同步链路，稳定后再叠加账号密码。账号是增值功能（跨设备），不是同步的前置条件。

- 已有纯本地用户升级为账号用户时，绑定流程的引导文案
